## Context
A review on 2026-08-14 found Part 0 shipped its own answers. `part-0.md` quoted
this repo's complete `pyproject.toml` ("Quoted from this repo's...") and its
`.gitignore` ("verbatim"), and every chapter-0 exercise was *verify this repo*
rather than *build a project*. Chapter 0's actual competency — stand up a modern
Python project — was never exercised; a reader read a finished implementation and
ran `echo $?` against it. RUL-0001 was intact for parts 1–7 (genuine scaffolds)
and totally broken for Part 0.

The same defect produced a concrete failure. `README.md` and `HOW-TO-USE.md`
assumed the repo was already present and *was* the student's project, so nothing
documented where the files come from or in what order they must be created. A
reader building the structure by hand hit two undocumented traps:
`readme = "README.md"` is a build-time pointer, so a missing README kills metadata
generation before any dependency resolves; and `packages = ["src/crash_course"]`
naming a directory that does not exist makes the editable install report success
while wiring up nothing.

The distinction that settles it: **instructions are not solutions — solutions are
implementations.** Telling a reader what to build and in what order is teaching.
Handing them the finished `pyproject.toml` to copy is the answer key.

## Decision
1. Part 0 has the reader build the course folder from an empty directory.
   Exercise 0.2 is *write `pyproject.toml` until these asserts pass*; the concept
   snippet shows table names, semantics, and elided values, never the assembled
   file. `.gitignore` is likewise pinned by asserts in 0.5, not quoted.
2. The two failure modes above become Exercise 0.3b — a loud build failure and a
   silent no-op install, run deliberately, side by side.
3. **One folder for the whole course.** The project built in Part 0 *is* the
   course folder; each `part-N.md` is downloaded into it as the reader reaches
   that part, and sits alongside `pyproject.toml`, `src/`, `tests/`, and
   `scratch.py`. There is no separate workbook checkout to keep in sync.
4. Parts are distributed from a **`release` branch** — a delivery channel, not a
   second workspace. Its purpose is that a reader can only ever download content
   that has passed the verification gate, and never downloads authoring material
   they have no use for. It carries `part-0…7.md`, `README.md`, `HOW-TO-USE.md`.
   Stripped: the anti-drift system (`CLAUDE.md`, `ANCHOR.md`, `STATE.md`, `wiki/`,
   `.claude/`, `WORKFLOW.md`, `RECREATE_PROMPT.md`, `SETUP.md`, `ARCHITECTURE.md`,
   `GLOSSARY.md`), the authoring specs (`SPEC.md`, `PROGRESS.md`), `tools/`, and —
   because they are now Part 0's answer key — `pyproject.toml`, `src/`, `tests/`.
5. `main` keeps `pyproject.toml`, `src/`, and `tests/` unchanged: DEC-0006 still
   requires this repo to be a real src-layout project with ruff/mypy/pytest green.
   Unverified or in-progress parts stay on `main` and never reach a reader.

## Alternatives considered
- Keep the repo as the running example, add only the missing setup instructions —
  rejected: leaves chapter 0's competency unexercised and the answer key shipped.
- Reader clones the workbook into its own directory, separate from the project
  they build — rejected: two directories to keep straight, and the parts belong
  next to the code they are worked in.
- Ship `pyproject.toml` on the release branch for reference — rejected: it is
  precisely Exercise 0.2's answer, one `curl` away.
- Branch `release` from `main` with dev files deleted — rejected: the anti-drift
  system would remain in the branch's history. `release` is an orphan branch.

## Consequences
Part 0 now teaches what it names, and its two hardest-won gotchas are content
rather than accidents. The reader ends Part 0 holding a real project that every
later chapter builds in, with the parts they have earned sitting in it. Readers
can never fetch an unverified part, and never see authoring machinery.

Costs: `part-0.md` no longer describes this repo's layout, so its claims are
verified against a constructed reference project in `/tmp/verify_part0.py` rather
than by running against the repo; every release needs the branch refreshed from
`main`, a manual step until automated; and `README.md` / `HOW-TO-USE.md` must stay
release-safe — no links to stripped files.
