## Context
As of 2026-08-14 the structure and content are substantially built and awaiting
hands-on review, and `release` exists as an orphan distribution branch (DEC-0009).
Two branches now carry meaning at once — what is being developed, and what a
student can download — and until now there was no way to say which commit on one
corresponds to which commit on the other. "The workbook as it stood on 14 August"
was not expressible, so a reader's problem could not be traced to a known state.

Direct authoring on `main` also leaves no record of *why* a change happened. The
content is now stable enough that changes are corrections to a known baseline
rather than construction, and corrections are worth documenting individually.

## Decision
**Branches.** `main` is the integration branch and holds everything: parts,
specs, tooling, and the anti-drift system. `release` is the orphan distribution
branch (DEC-0009), never developed on and never merged into — it is *rebuilt*
from `main` and only ever gains commits that way.

**Tracked issues, not contributor drive-bys.** This repo runs the production
model: **GitHub Issues is the tracker** and owns the problem and its status; the
PR owns the change. They are separate artifacts and neither substitutes for the
other. A ticket exists from the moment a problem is understood, whether or not
anyone is working on it yet — that is what makes progress monitorable and what
makes a draft PR meaningful when work starts.

The sequence, per issue:

1. **Ticket first.** The issue is written up on discovery — observation,
   evidence, root cause, and how a fix would be verified — and filed with
   `gh issue create`. It gets a type label (`bug` / `content` / `tooling`).
   Nothing is branched yet; a ticket with no branch is a valid, useful state.
2. **Branch** off `main` when work starts, named `fix/<N>-<slug>` after the
   ticket number, so branch, PR, and ticket are greppable as one unit.
3. **Draft PR as soon as the first commit of real work lands** — typically the
   reproduction: the failing assert, verify case, or documented repro that
   demonstrates the defect. Body carries `Closes #N`. From here the PR is the
   working surface: CI runs on every push, review can start before the fix is
   finished.
4. **Fix commits** land on the same branch.
5. **Ready for review** (`gh pr ready`) once the affected parts are green
   (RUL-0002). Merge closes the ticket automatically via `Closes #N`. Squash or
   merge is the human's call.

The draft opens after the first commit rather than before it because GitHub
cannot open a PR from a branch identical to its base — with a tracker in place
there is no need to invent a doc-only commit to get around that, since the
write-up already lives in the ticket.

**Agents do not write to GitHub.** RUL-0004 forbids remote writes: an agent
drafts the ticket body, the branch, and the commits, then hands over the exact
`gh issue create`, `git push`, `gh pr create --draft`, and `gh pr ready`
commands. Read-only tracker access (`gh issue list`, `gh issue view`,
`gh pr view`) is allowed and is how an agent picks up ticket context at the start
of a session.

**Deriving a release.** After merges land on `main` and the affected parts are
green (RUL-0002), rebuild `release` from that exact `main` commit with
`tools/build-release.sh`. The rebuild is a fresh commit on top of the existing
`release` history, so `release` keeps a readable log of published versions while
never sharing history with `main`.

**Baselines.** A baseline pins both branches with paired annotated tags —
`baseline/vX.Y` on `main`, `release/vX.Y` on `release` — and gets a row in
`VERSIONS.md` recording date, status, and scope. Tags carry the link to the
commits; `VERSIONS.md` carries the meaning. MINOR for a batch of fixes, MAJOR for
structural change to how the course is worked. `v1.0` is the first
hands-on-reviewed baseline.

## Alternatives considered
- Merge `main` into `release` — rejected: `release` is an orphan by design
  (DEC-0009), and a merge would drag the anti-drift system into its history.
- A single tag on `main` only — rejected: it cannot express which published
  files a student actually downloaded, which is the question a bug report raises.
- Version in a file (`VERSION`) rather than tags — rejected: a file cannot name
  the commit it lives in without circularity; tags resolve exactly.
- Direct commits to `main` for small fixes — rejected: the per-issue record is
  the point, and "small" is the category that most often needs the trail later.
- Opening the PR after the fix is complete (the common drive-by-contributor
  flow) — rejected: that model suits open-source contribution, where a
  maintainer wants to see finished work and no ticket exists beforehand. This
  repo is run production-style, with tickets tracking problems independently of
  who is fixing them, so the PR opens as a draft when work starts.
- The PR as the only artifact, doubling as the issue record — rejected: it
  cannot represent a known problem that nobody has started, which is precisely
  the state a tracker exists to show.
- An in-repo issue log (`issues/*.md`) so agents could file tickets directly —
  rejected: it re-implements a tracker, loses the board, labels, and
  close-on-merge, and creates a second record that drifts from GitHub's.

## Consequences
Any reported problem can be tied to a baseline, to the ticket that recorded it,
and to the PR that changed it — and the backlog shows problems that are known
but unstarted, which a PR-only model cannot represent.

The cost is ceremony on every fix — a ticket, a branch, a draft PR, and a
release rebuild for anything that touches a part file — plus three human
handoffs per issue under RUL-0004 (`gh issue create`, the pushes, `gh pr ready`),
since agents may read the tracker but never write to it. Changes touching only authoring material
(`wiki/`, `SPEC.md`, `STATE.md`, `tools/`) do not require a release rebuild,
since the published tree is unchanged; the ledger only moves when readers'
files move. Tagging and pushing stay manual under RUL-0004, so declaring a
baseline is deliberately a human act.
