title: Re-read remote state at the moment you assert it; never from an earlier snapshot

summary: Any read of issue, PR, branch, or remote state is perishable — re-run the check immediately before stating that state, and never infer that a handed-off command was run.
applies_to: every claim about issue, PR, branch, merge, or remote state; every handoff under RUL-0004

## Rule
State that lives on the remote — issue status, PR draft/merged status, branch
tips, labels, what `origin/main` points at — is changed by the human, not by the
agent (RUL-0004). Treat every read of it as valid only at the instant it was
taken.

Concretely:

1. **The trigger is vocabulary, not intent.** GLOSSARY.md's *Perishable
   vocabulary* table lists the terms that demand a Fresh read — lifecycle words
   (merged, open, draft), sync words (pushed, ahead, in sync), completion words
   (done, blocked, outstanding), recency adverbs (now, already, still), derived
   numbers, and the inference verbs that impersonate reads (should be, must
   have, by now). Writing one about an externally-mutable artifact requires the
   check to have run **in the same turn, after the last event that could have
   changed it**. Apply the test: *could a command run outside this session change
   whether this sentence is true?*
2. **Do not carry state forward.** Never restate a value read in an earlier
   turn, and never re-print a status table. Recompute it or drop it.
3. **Never claim freshness you do not have.** "Verified just now", "re-read
   rather than recalled" — these are themselves perishable claims and are
   permitted only with the command output in the same turn. A false freshness
   claim is worse than a stale value, because it removes the reader's cue to
   check.
4. **Never infer completion.** A handed-off command is not done because it was
   handed off, and not done because one downstream signal looks consistent with
   it. Verify the specific step — a PR existing does not prove its body was
   updated, and a branch being ahead does not prove it was pushed.
5. **Unexpected output means check the workflow, not just the tool.** When the
   human reports a surprising result, first establish where the process actually
   is and name the step that is incomplete. Explaining why a tool's output is
   internally correct, without checking whether the workflow stalled, is the
   failure this clause exists to prevent.
6. **Report the step, not the vibe.** Say which step is done and which is not,
   with the evidence that settled it.

## Rationale
Under RUL-0004 the agent never writes to the remote, so the human acts in
parallel and the agent's picture of the remote goes stale the moment it is
taken. On 2026-08-14, during issue #1 / PR #2, an agent read `mergedAt: null`,
then wrote a status table in a later response asserting the PR was unmerged and
the flow was blocked. The merge had landed at 21:29:06Z, before that response.
The same session produced the mirror-image error minutes earlier: when
`build-release.sh` reported "nothing to do", the agent explained that the script
was behaving correctly instead of reporting that the merge had never happened —
correct about the tool, wrong about the process.

Stale state asserted confidently is worse than no state: it sends the human to
debug a problem that does not exist, or to redo a step already taken.

**This rule was violated in the same session that produced it.** Minutes after
being written, the agent printed a status table for issues #1 and #3 in a turn
whose only commands were `mv`, `git checkout`, and `git commit` — no state read
at all — and labelled it "each re-read just now rather than recalled." The first
draft of this rule triggered on *being about to assert*, which cannot catch the
case where a status table feels like summarizing work already done rather than
making a fresh claim. The user's correction: bind the trigger to **vocabulary**
instead of intent, so the check fires on the words themselves regardless of how
the sentence feels to write. A turn-start check was considered and rejected — it
degrades into one read at the top of a turn and stale assertions after it.

## Applying it
Before sending any message containing a term from GLOSSARY.md's Perishable
vocabulary table, confirm the fresh read is in this turn. If it is not, either
run it, or write "as of <time>, X was Y" and say the check is stale.

## Exceptions
Facts that cannot have changed without the agent seeing it — the content of a
local file it just wrote, or a command's output within the same turn — may be
stated without re-reading. Anything touching the remote may not.
